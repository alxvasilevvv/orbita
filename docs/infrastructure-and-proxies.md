# Прокси и дополнительные инструменты: анализ

Дата анализа: 2026-10-02. Документ отвечает на вопрос «какие прокси и внешние инструменты нужны платформе» и отделяет то, что нужно, от того, что вредно.

## 1. Главный вывод

Прокси для LinkedIn в смысле «обхода» (резидентные, мобильные, ротация IP под каждого клиента, антидетект-браузеры, импорт cookies, решатели CAPTCHA) платформе **не нужны и запрещены**:

- Официальный API авторизуется OAuth-токеном конкретного участника или администратора страницы. IP сервера не влияет на то, «от кого» действие; маскировка IP ничего не даёт.
- LinkedIn прямо запрещает сторонние инструменты автоматизации сайта и сбор данных ([Prohibited software and extensions](https://www.linkedin.com/help/linkedin/answer/a1341387), [Automated activity on LinkedIn](https://www.linkedin.com/help/linkedin/answer/90586)). Нарушение ведёт к ограничению **клиентских** аккаунтов: это прямой риск для агентства и его репутации.
- Мастер-промпт (п. 3.3) запрещает скрытую автоматизацию, cookies и маскировку массовой активности.

Нужны другие классы прокси и инструментов: для безопасности, наблюдаемости и контроля исходящего трафика. Ниже по приоритету.

## 2. Что нужно: обязательный минимум (этапы 1–2)

| # | Инструмент | Зачем именно нам | Варианты | Этап |
|---|---|---|---|---|
| 1 | **Identity-aware proxy + IdP с MFA** | Вход сотрудников с MFA; приложение в режиме `AUTH_MODE=header` доверяет только заголовку от прокси. Мгновенный отзыв доступа при увольнении | oauth2-proxy или Pomerium перед приложением + Google Workspace / Microsoft Entra / Okta; для клиентского кабинета отдельный арендатор (magic link + MFA) | 1 |
| 2 | **Reverse proxy / ingress с TLS и WAF** | HTTPS, HSTS, лимиты запросов на /api, защита OAuth callback, базовый WAF | Cloudflare (WAF, Zero Trust) или Caddy/NGINX на хосте; на Kubernetes ingress-nginx | 1 |
| 3 | **Egress-прокси со статическим IP и allowlist доменов** | Исходящие запросы только на `api.linkedin.com`, `www.linkedin.com/oauth`, AI-провайдера, S3, почту. Журнал всех внешних вызовов. Защита от SSRF в функциях, которые ходят по ссылкам (превью статей). Один стабильный IP для обращений в поддержку LinkedIn | NAT gateway облака + Squid/Envoy с allowlist, либо Cloudflare Zero Trust egress; в Kubernetes NetworkPolicy + egress gateway | 2 |
| 4 | **Менеджер секретов / KMS** | OAuth-токены клиентов. Сейчас в коде `DbSecretStore` (AES-256-GCM, ключ вне БД); в production ключ из KMS, ротация | AWS Secrets Manager + KMS, HashiCorp Vault, Doppler, 1Password Secrets Automation | 1 |
| 5 | **Управляемый PostgreSQL с PITR** | Основная БД и очередь публикаций (`FOR UPDATE`/атомарный захват). RPO ≤ 1 ч требует point-in-time recovery | AWS RDS / Aurora, Google Cloud SQL, Neon, Supabase (у вас уже подключён) | 1 |
| 6 | **S3-совместимое хранилище + антивирус** | Медиа клиентов, подписанные ссылки с коротким сроком, префикс на клиента для изоляции и удаления | AWS S3, Cloudflare R2; ClamAV в отдельном worker | 2 |
| 7 | **Наблюдаемость** | Трассировки до вызова LinkedIn, метрики очереди (возраст задания, unknown, dead), алерты. Доступность LinkedIn показывается отдельно от нашей | OpenTelemetry → Grafana Cloud / Sentry / Better Stack; лог-пайплайн с редактированием секретов (в Fastify уже отключены `authorization` и `cookie`) | 1–2 |
| 8 | **Транзакционная почта и уведомления** | Согласования клиенту, напоминания, инциденты; дедупликация уже в outbox | Postmark, AWS SES; вебхуки Slack / Telegram для команды | 1 |

## 3. Что нужно: ускорители (этапы 3–4)

| Инструмент | Зачем | Варианты |
|---|---|---|
| **AI-шлюз** | Единая точка для всех AI-ролей: ключи не в коде, бюджет и лимит стоимости на клиента, редактирование PII в логах, fallback моделей, запрет обучения на данных | LiteLLM (self-hosted), Portkey, Cloudflare AI Gateway. Адаптер `AiProvider` в `src/ai/guard.ts` уже изолирует провайдера |
| **Корпоративный VPN / Zero Trust для сотрудников** | Админ-доступ к инфраструктуре; сотрудникам в регионах, где LinkedIn заблокирован (например, в РФ с 2016 года), нужен стабильный корпоративный выход для assisted-задач по страницам компаний. Один постоянный IP на сотрудника, не ротация под клиента | Tailscale, Cloudflare WARP / Zero Trust, WireGuard на собственном шлюзе |
| **Импорт аналитики** | Пока Community Management API не одобрен: разбор выгрузок аналитики страниц и creator analytics (XLSX/CSV), загруженных уполномоченным человеком | Встроенный парсер (sheetjs) поверх `POST /api/accounts/:id/metrics`; идемпотентность через `import_batch_key` уже есть |
| **CRM** | Модуль возможностей: события сделок из CRM как источник атрибуции `crm_event` | HubSpot, Pipedrive, amoCRM через официальные API и вебхуки |
| **Обработка медиа** | Проверка форматов/размеров до загрузки в LinkedIn Images/Videos API, превью | sharp, ffmpeg в отдельном worker |
| **Feature flags** | Включать API-режим по мере одобрения продуктов, без релиза | Unleash, Flagsmith или таблица настроек |
| **Нагрузочное тестирование** | Проверка ориентиров 500 / 2 000 аккаунтов на стенде, без живого LinkedIn | k6 + демо-адаптер |

## 4. Важное ограничение, которое меняет процессы

LinkedIn не поддерживает делегирование личного профиля третьим лицам. Передача пароля клиента сотруднику агентства нарушает пользовательское соглашение LinkedIn и противоречит п. 3.1 промпта. Поэтому:

- **Страницы компаний**: сотрудник агентства получает роль администратора страницы (Content admin) от клиента. Assisted-публикацию выполняет он сам из своего аккаунта, а при одобрении Community Management API работает автоматическая публикация.
- **Личные профили**: публикацию выполняет либо API по OAuth самого владельца (Share on LinkedIn, `w_member_social`, self-serve), либо сам владелец по assisted-задаче с готовым текстом. Сотрудник агентства в чужой профиль не входит.

Это главная причина, по которой «прокси для входа в аккаунты клиентов» не нужен: такого входа в правильно построенном процессе нет.

## 5. Что подключить в первую очередь

1. Приложение в LinkedIn Developer Portal с продуктами **Sign In with LinkedIn using OpenID Connect** и **Share on LinkedIn** (self-serve, без проверки). После этого в `.env` указать `LINKEDIN_APPROVED_PRODUCTS`, и публикация в личные профили переходит в режим API.
2. Подать заявку на **Community Management API** (Development tier → Standard tier со скринкастом каждого сценария) отдельным новым приложением: этот продукт нельзя запросить в приложении, где уже есть другие продукты ([Community Management overview](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/community-management-overview)).
3. IdP с MFA + oauth2-proxy, managed Postgres с PITR, менеджер секретов, Sentry. С этим можно запускать пилот на десятках аккаунтов.
4. Egress-прокси и AI-шлюз до подключения AI к реальным данным клиентов.
