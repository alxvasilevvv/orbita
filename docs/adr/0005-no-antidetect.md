# ADR 0005. Без антидетект-браузеров, ротации прокси и мультиаккаунтинга

Статус: принято, 2026-10-16.

## Контекст

Рассматривались инструменты вроде Multilogin: изолированные браузерные профили с подменой отпечатков, резидентные и мобильные прокси с ротацией, облачные телефоны, перенос куки, автоматизация через Selenium, Playwright и Puppeteer. Их назначение: вести много аккаунтов LinkedIn с одной инфраструктуры и скрыть это от платформы.

## Решение

Платформа такие механизмы не использует и не интегрирует.

## Причины

1. LinkedIn запрещает сторонние инструменты автоматизации и маскировку (User Agreement 8.2, Prohibited software and extensions). Это не серая зона.
2. В нашей модели аккаунты принадлежат реальным сотрудникам клиентов. Если инфраструктура связывает много аккаунтов, ограничение получают все сразу, вместе со страницей компании. Ровно этот риск клиент просит исключить.
3. Изоляция, ради которой обычно берут антидетект, у нас решена правильным способом. У каждого сотрудника свой вход и свой аккаунт. Действие выполняет сам владелец или официальный API по его OAuth-токену. Каждое действие одобряется отдельно, лимиты и офицер безопасности работают на стороне платформы.
4. Для криптовалютных и финансовых клиентов маскировка активности создаёт дополнительный регуляторный риск (раскрытие связи с работодателем, правила продвижения).

## Что используем вместо этого

Офицер безопасности: лимиты, разгон, охлаждение по сигналам, правила естественности, проверка текстов. Официальные API LinkedIn после одобрения продуктов. Выполнение действий самим сотрудником с отметкой «Сделал». Egress-прокси только для контроля исходящего трафика сервера (см. `infrastructure-and-proxies.md`), без ротации и маскировки.

## Официальный API против браузерной автоматизации: сравнение и вердикт (2026-10-16)

Клиент предлагал вести аккаунты через облачные браузеры (Browserbase с Agent Identity, обход капчи) и агентов, аргумент: больше функционала и «имитация живого человека исключает блокировку». Разобрали оба пути.

Потолок официального API (факт на 2026): посты и репосты от своего имени есть (Share on LinkedIn, `w_member_social`); комментарии и реакции только через Community Management API (партнёрский доступ, не свободный лайк и комментарий по любому чужому контенту; AI-комментарии к чужому контенту запрещены Developer AI Policy); приглашений в контакты, личных сообщений, поиска людей и аналитики по чужим профилям официального API нет. Поиск в самом продукте ограничен Commercial Use Limit (около 300 в месяц на Free и Premium Career).

Браузерный путь даёт полный функционал, но не исключает блокировку, а является её главной причиной. LinkedIn ловит автоматизацию поведенческим анализом, отпечатком браузера и мониторингом запросов; «человечные» медленные боты всё равно вылетают из-за ровного паттерна; «undetectable» не держится; обход капчи и маскировка это отдельное нарушение User Agreement 8.2. Наказание лестницей: ограничение 1–7 дней, затем приостановка с проверкой личности, затем вечный бан без апелляции. На 30 аккаунтах с общей инфраструктуры риск коррелирован: ограничение прилетает всей связке и странице компании разом. Аналогия с личным аккаунтом владельца не переносится: там один аккаунт, владелец видит работу и сам несёт риск; здесь 30 чужих аккаунтов под маскировкой и ответственность на агентстве. Для криптобренда, который строит доверие, публичный провал это репутационный удар.

Вердикт: гибрид. Сервер через официальный API делает безопасную объёмную часть (посты, репосты, аналитика страницы). Подключения, личные сообщения, лайки и комментарии к чужому контенту, Sales Navigator (то, что API не умеет и что несёт максимальный риск бана) агент готовит, а сотрудник отправляет одним касанием из Telegram или кабинета. Это даёт почти весь функционал браузерного пути без коррелированного катастрофического риска. Централизованную стелс-ферму из чужих аккаунтов не строим. Решение действует для X (Twitter) и других сетей: тот же гибрид поверх официального API сети.
