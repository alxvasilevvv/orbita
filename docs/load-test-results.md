# Нагрузочные испытания

Дата: 2026-10-03. Скрипт: `scripts/loadtest.ts` (воспроизводимый: `THINK_MS=1000 DATABASE_URL=postgres://… npx tsx scripts/loadtest.ts 500 30`).

Стенд: песочница с **2 vCPU**, PostgreSQL 16 и API (один процесс Node.js 22) на одной машине вместе с генератором нагрузки. Все запросы идут через RLS (роль `app_user`), 50 разных сотрудников уровня агентства, у каждого ~N/50 аккаунтов.

Сценарии: реестр аккаунтов (100 строк), реестр с фильтром внимания, обзор агентства, рабочее пространство аккаунта, центр согласований, задачи, календарь на месяц.

## Итог относительно проектных целей

| Цель | Результат |
|---|---|
| 500 аккаунтов, 50 сотрудников, p95 чтений ≤ 800 мс | **Выполнено**: реалистичный режим p95 32–70 мс; даже без пауз между действиями p95 ≤ 647 мс |
| 2 000 аккаунтов | **Выполнено в реалистичном режиме**: p95 127–381 мс. В стресс-режиме без пауз (≈ 58 запр/с на 2 ядрах) p95 обзора 1,5 с: предел этого железа, а не архитектуры |
| Ошибки под нагрузкой | 0 во всех прогонах |

Что дало основной выигрыш после первого прогона (тогда p95 доходил до 22 с):
1. Политики RLS переписаны с функции на каждую строку на хешированный подзапрос `client_id IN (SELECT unnest(…))`: подсчёт 10 500 строк 12 мс вместо 7 с (миграция 006).
2. Параметры области и смена роли отправляются вместе с BEGIN одним обращением к базе.
3. Пользователь и его роли загружаются одним запросом.
4. Список задач ограничен 200 строками по приоритету, календарь фильтруется по своим аккаунтам.

Для 2 000 аккаунтов в production рекомендуется 2 экземпляра API по 2 vCPU и PostgreSQL на отдельном узле (4 vCPU). Цифры остаются проектными до повторения на согласованном стенде.
