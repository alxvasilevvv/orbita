# Agency LinkedIn OS: архитектура и спецификация

## 1. Продукт

Внутренняя платформа SMM-агентства для ведения сотен клиентских LinkedIn-профилей и страниц компаний: стратегия на каждый аккаунт, контент с версиями и согласованием конкретной версии, публикация через официальный API или через человека, журнал действий с типом доказательства, задачи, отчёты клиенту, экономика агентства и AI-помощники без права внешних действий.

Главный критерий: агентство видит реальную выполненную работу и подтверждённые результаты и контролирует каждое внешнее действие.

## 2. Допущения и открытые вопросы

Допущения (приняты без вопросов, можно пересмотреть):
- Нагрузка: 500 активных аккаунтов, рост до 2 000, до 50 сотрудников одновременно.
- Приложение LinkedIn ещё не создано; по умолчанию все операции в режиме «через человека».
- Очередь публикаций хранится в PostgreSQL, а не в Redis (ADR 0002): объём сотни-тысячи заданий в сутки, нужна транзакционность с бизнес-данными.
- Вход сотрудников через внешний IdP с MFA (ADR 0003); в dev используется переключатель пользователей.
- Основной язык интерфейса русский, контент клиентов на любом языке.

Открытые вопросы, влияющие на архитектуру:
1. Регион хранения данных и список допустимых субпроцессоров (AI-провайдер, облако).
2. Будет ли клиентский кабинет на отдельном домене и IdP.
3. Какие CRM клиентов нужно поддержать первыми.

## 3. Модули (модульный монолит)

```
src/
  core/            чистая доменная логика без БД: права, машина состояний, время/DST,
                   метрики, реестр возможностей, эвристики, шаблоны стратегий
  ai/              ограждения AI: изоляция контекста, внешний текст как данные, схема вывода
  integrations/    единый контракт SocialAdapter; LinkedInHttpAdapter и DemoLinkedInAdapter
  services/        сценарии с проверкой прав на сервере и транзакциями
    accounts.ts    Clients & Accounts, Consent, Integrations & Capabilities, Strategy & Knowledge
    content.ts     Content, Approvals, AI-черновик
    publishing.ts  Publishing: очередь, исполнитель, unknown, assisted, аварийная пауза
    operations.ts  Tasks, Analytics & Reports, Opportunities, Team, Audit
  server/          HTTP API (Fastify), OAuth LinkedIn
  worker/          отдельный процесс исполнителя
  ui/              React SPA

```

Соответствие 14 модулям промпта: Identity & Access (`permissions.ts`, `context.ts`), Clients & Accounts, Integrations & Capabilities, Strategy & Knowledge (`accounts.ts`), Content & Assets, Approvals (`content.ts`), Publishing (`publishing.ts`), Tasks & Workflows, Analytics & Reports, Opportunities, Team Operations (`operations.ts`), Engagement (каркас: эвристика и таблицы, UI на этапе 3), AI Orchestration (`ai/`), Audit & Data Lifecycle (`audit_events`, `retention_policies`).

## 4. Модель данных

Полная схема: `migrations/001_core.sql`. Ключевые правила:
- Все клиентские таблицы содержат `client_id` (NOT NULL) и, где применимо, `account_id`. Сервис выводит `client_id` из аккаунта на сервере и не принимает его из запроса.
- Удаление клиента и аккаунта `ON DELETE RESTRICT`: удаление идёт процедурой жизненного цикла, а не каскадом.
- Время в `timestamptz` (UTC); часовой пояс аккаунта хранится отдельно и в `content_items.scheduled_tz`.
- `metric_snapshots.value` допускает NULL: это отсутствие данных, `availability_status` объясняет причину.
- `action_records.evidence_type`: `api_confirmed` | `manual_mark` | `unconfirmed`.
- `audit_events` хранит метаданные, а не тексты клиентов (проверяется тестом).
- `publication_jobs.idempotency_key` уникален: материал + согласованная версия.
- Индексы: очередь `publication_jobs(run_at) WHERE status IN (queued, leased)`, реестр возможностей `(account_id, operation, checked_at DESC)`, метрики `(account_id, metric_key, observed_at DESC)`, дедупликация импорта по `import_batch_key`.

## 5. Машины состояний

Контент (`src/core/contentStateMachine.ts`):

```
idea → brief → draft → editorial_review → client_review → approved → scheduled → publishing → published
                 ↑            │                  │            │           │            ├→ failed
                 └── changes_requested ←─────────┘            │           │            └→ publication_unknown
новая версия в editorial_review / client_review / approved / scheduled → draft (согласования аннулируются)
```

Для каждого перехода в коде заданы: требуемая операция (или `system`), обязательные данные, событие аудита, получатели уведомлений, способ отмены.

Задание публикации: `queued → leased → succeeded | queued (повтор) | failed | dead | unknown | awaiting_human | cancelled`.

## 6. Алгоритмы

### 6.1. Публикация (`executeJob`)
- Вход: задание, согласованная версия, подключение, согласия, возможности.
- Проверка качества: версия задания = согласованная = текущая; нет блокирующих пометок, запрещённых тем, сигналов поиска работы при конфиденциальном режиме.
- Условия запуска: `status = queued`, `mode = api`, `run_at <= now`; не более одного задания на аккаунт за проход (справедливость).
- Логика: атомарный захват → проверки → `publishing` → запись ActionRecord `requested` → внешний вызов → результат.
- Выход: `published` с внешним ID и `api_confirmed`.
- Ошибки: квота/временная → повтор с экспоненциальной задержкой и jitter; постоянная → `failed` + задача; авторизация → подключение `error` + задача переподключения; потеря ответа → `publication_unknown`, проверка доступным способом, иначе задача человеку; исчерпаны попытки → `dead` + инцидент; сбой исполнителя с истёкшей арендой → `unknown`.
- Действия человека: разрешить неопределённость, переподключить, разобрать ошибку.
- Аудит: каждое изменение состояния, блокировки с кодами.
- Успех: ровно одна публикация на ключ идемпотентности в нашей системе; во внешней системе exactly-once не обещается.

### 6.2. Определение возможностей (`resolveCapabilities`)
Вход: тип аккаунта, статус подключения, выданные scopes, одобренные продукты приложения. Операция в режиме API только при выполнении всех трёх условий; иначе резервный режим с причиной и альтернативой. Запуск: создание аккаунта, OAuth, отзыв, ручная проверка; перед публикацией читается актуальный снимок.

### 6.3. Календарь и DST (`resolveLocal`)
Локальное время в поясе аккаунта → UTC. Несуществующее время (переход на летнее) отклоняется с подсказкой; повторяющееся требует явного выбора «раньше/позже». Время публикации никогда не сдвигается молча.

### 6.4. Подготовка контента AI (`aiDraft`)
Вход: подтверждённые факты только этого аккаунта, цель, тема, необязательный внешний текст. Требует согласия `ai_processing`. Внешний текст оборачивается в `<untrusted_source>` и проверяется на инструкции. Без фактов черновик содержит блокирующую пометку `[НУЖНО ОТ КЛИЕНТА: …]`. Результат сохраняется как версия `ai_draft`; публиковать AI не может. Сохраняются провайдер, модель, версия промпта, источники, стоимость.

### 6.5. Приоритет задач и взаимодействий (`heuristics.ts`)
`priority = 0.40 × urgency + 0.35 × impact + 0.25 × blocker_severity`; `engagement = 0.30 × relevance + 0.25 × audience_fit + 0.25 × contribution_value + 0.20 × timeliness`. Компоненты нормализуются 0–1, веса настраиваются, блокировки дают `score = null`. Назначение сверх ёмкости требует явного подтверждения.

### 6.6. Аналитика (`metrics.ts`)
NULL не превращается в 0; накопительные снимки берутся последним значением; охват и показы не смешиваются; уникальный охват не суммируется; interaction rate и CTR возвращают «не рассчитывается» без совместимого знаменателя. Еженедельный пересмотр стратегии (этап 4): медианы по сопоставимым публикациям, явная пометка малых выборок, формулировка «последовательный эксперимент».

## 8. Модель полномочий AI

- Роли: стратег, автор, редактор, проверяющий факты, аналитик, планировщик, помощник по взаимодействиям, автор отчётов. Каждой роли собирается контекст одного аккаунта (`buildIsolatedContext` отклоняет чужие источники).
- AI не имеет доступа к токенам, адаптеру публикации и SQL. Разрешённые «действия» только предложения: черновик, замечания, вопрос клиенту, задача.
- Внешний текст = данные. Инструкции внутри помечаются риском и блокируют публикацию до проверки человеком.
- Источники с `usage_rights = internal_only` в AI не передаются. API-данные LinkedIn в AI не передаются, пока не подтверждены разрешённые цели использования (Marketing API Terms).
- Вывод проверяется схемой (`AiOutputSchema`), `requires_approval` всегда `true`.

## 9. Безопасность и данные

Сделано: проверки на сервере, 404 для чужих объектов, MFA через IdP (production), секреты AES-256-GCM вне логов, редактирование заголовков авторизации в логах, OAuth `state`, аудит чувствительных операций, отзыв доступа при увольнении, пауза публикации на трёх уровнях, отзыв согласия отменяет неотправленные действия, классы данных в `retention_policies`.

Осталось: процедура удаления клиента по всем хранилищам (БД, S3-префикс, кэш, индексы, бэкапы по циклу ротации), подписанные ссылки и антивирус для медиа, Row Level Security в PostgreSQL как второй рубеж изоляции, проверенное восстановление из бэкапа.

## 11. План тестирования

- Модульные (`test/core.test.ts`): DST, метрики, возможности, права, машина состояний, эвристики, AI-ограждения.
- Интеграционные (`test/flow.test.ts`) на реальном PostgreSQL (PGlite): изоляция через сервисы и HTTP, согласование и его аннулирование, assisted и API-публикация, идемпотентность, параллельные исполнители, потеря ответа, отзыв согласия и подключения, квоты, сбой исполнителя, массовые операции, импорт метрик, отчёт, ёмкость, увольнение, отсутствие текстов в аудите.
- Контрактные тесты адаптера LinkedIn: на записанных ответах (этап 2). Живой LinkedIn в автотестах не используется.
- Сквозные: Playwright-сценарий по UI (см. README).

## 12. Эксплуатация и расходы

Бюджет запросов в сутки:
`total = ceil((accounts × syncs_per_day × requests_per_sync + publications × requests_per_publication + interactions) × (1 + reserve))`

При 4 синхронизациях × 3 запроса, 0,4 публикации на аккаунт × 2 запроса, 1 взаимодействии на аккаунт и резерве 30%:
- 500 аккаунтов: 8 970 запросов в сутки.
- 2 000 аккаунтов: 35 880 запросов в сутки.

Если квота приложения меньше, частота синхронизации снижается, а интерфейс показывает свежесть данных. Лимит на участника проверяется локально (`MEMBER_DAILY_REQUEST_BUDGET`).

Ежемесячные расходы (без выдуманных цен):
`infra = db + 2 × app + 2 × worker + storage_GB × price_GB + egress + observability`
`ai = Σ(tokens_in × price_in + tokens_out × price_out)` по `ai_executions`, лимит на клиента в AI-шлюзе
`client_cost = minutes × internal_rate / 60 + ai_cost + allocated_overhead`

Стартовая конфигурация для 500 аккаунтов: managed PostgreSQL 2–4 vCPU / 8–16 GB с PITR, 2 экземпляра API, 2 исполнителя, S3, Sentry. Все цифры являются проектными целями до нагрузочного теста.
